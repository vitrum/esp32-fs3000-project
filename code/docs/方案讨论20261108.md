# Aero post 骑行码表技术方案

> 本文整理自 2026-11-08 关于 ESP32 骑行码表（Aero post 风阻量化码表）的多轮技术讨论，覆盖传感器选型、供电、显示、双 IMU 姿态识别、通信、算法与实施路线。
>
> 标记约定：
>
> - **【已定】** 讨论中已明确的结论或技术路线。
> - **【待验证】** 需要实物测试或查阅原始资料确认的数据与判断，不要直接当作定论使用。
> - **【局限】** 当前方案固有的能力边界，需在设计与对外说明中体现。

---

## 0. 项目目标与边界

### 0.1 目标

在自研骑行码表上实现**骑行姿态的连续量化**，输出姿态因子，与车速、相对风速、功率联合反算气动阻力系数（CdA），并映射为 7 级气动分区（产品化命名 Aero post）。

### 0.2 明确不做的事

- 不做导航级地图与轨迹规划（与 Garmin Edge 系列定位区分）。
- 不做医疗或运动生理结论输出，SmO₂、sEMG 等仅作数据采集预留，不进入本版算法。
- 第一阶段不追求"无限续航"，太阳能仅作涓流补电。

### 0.3 关键差异化

商用码表（Garmin Edge Solar 等）解决的是"续航 + 导航"；本项目解决的是**姿势—风阻的因果量化**，即回答"当前这个姿势值多少瓦"。

## 1. 系统总体架构

```
[太阳能板 1.5V/5V]
        │
        ▼
[MPPT 低压充电模块 CN3065 / CN3791]
        │
        ▼
[3.7V 锂电池 + 保护板]  ──► [电源门控 MOS] ──► [各负载独立供电]
                                                    │
                     ┌──────────────────────────────┼──────────────────┐
                     ▼                              ▼                  ▼
            [ESP32-S3 主板]                  [AFS3000 风速]        [GNSS 模块]
              ├─ 板载六轴 IMU（车架基准）
              ├─ 半反射显示屏
              └─ BLE 主机
                     ▲
                     │ BLE（一期） / ESP-NOW（二期）
                     │
              [前臂六轴 IMU 节点]
```

分层理解：

| 层     | 内容                                   | 说明               |
| ------ | -------------------------------------- | ------------------ |
| 能源层 | 太阳能板 → MPPT → 锂电 → 门控       | 决定能不能撑住一天 |
| 感知层 | 板载 IMU、前臂 IMU、风速、GNSS、功率计 | 决定数据质量       |
| 融合层 | 相对姿态解算、姿态打分、CdA 反算       | 决定产品价值       |
| 交互层 | 半反射屏、按键、日志落盘               | 决定可用性         |

## 2. 风速传感方案

### 2.1 选型原则【已定】

1. 必须是**热式 MEMS**（无机械转动部件，抗震）。
2. 必须是 **I2C 数字输出**，不要 0–5V 模拟量（ESP32 采集麻烦且精度差）。
3. 供电优先 **3.3V**，避免电平转换。
4. 必须具备**温度补偿**，否则气温变化直接造成风速漂移。
5. 量程覆盖骑行场景即可，不必追求实验室级全量程。

### 2.2 候选型号对照

| 型号              | 量程          | 接口        | 供电    | 定位       | 备注                         |
| ----------------- | ------------- | ----------- | ------- | ---------- | ---------------------------- |
| AFS3000           | 约 0–20 m/s  | I2C         | 3.3V    | 原配主选   | 出厂校准，代码生态较成熟     |
| FS3000-1005       | 约 0–7.2 m/s | I2C         | 3.3V    | 低速微风   | 量程偏小，不适合高速骑行     |
| PAV3015           | 约 0–15 m/s  | I2C（0x28） | 3.3–5V | 抗漂移替代 | 响应快，无机械结构           |
| AFM3001 / AFM3000 | 约 0–20 m/s  | I2C         | 3.3V    | 同厂精简版 | 引脚兼容性较好，代码复用度高 |
| CJMCU-S12D 类模块 | 约 0–12 m/s  | I2C         | 3.3V    | 低成本     | 适合便携、电池供电           |

> 【待验证】上表量程、地址、精度、响应时间为讨论中依据厂商公开资料归纳，下单前请在对应厂商官网 datasheet 逐项核对，尤其是 I2C 地址与转换公式（各型号标定系数不同，不能直接套用）。

### 2.3 关键工程约束

- **风速必须测"相对风速"，不是环境风速。** 车上安装位置若在车头迎风处，测得的是车速与自然风的合成气流，这正是 CdA 反算需要的量；若安装在车把后方负压区，读数会被系统性低估，必须在标定阶段修正。
- **安装姿态影响读数。** 热式传感器的敏感方向是固定的，安装时须保证感应通道与骑行前进方向一致，偏角会带来余弦误差。
- **需要做零点标定。** 静止无风环境下读取基线值，作为后续所有读数的零点偏移。

## 3. 供电与能源方案

### 3.1 手头太阳能板的实测参数【已定】

| 项目     | 数值                                  |
| -------- | ------------------------------------- |
| 尺寸     | 30 × 36 mm，厚度 2.5 ± 0.3 mm       |
| 重量     | 约 3 g                                |
| 额定     | 1.5V / 70 mA                          |
| 开路电压 | 约 1.8 V                              |
| 短路电流 | 约 77 mA                              |
| 峰值功率 | 约 0.12 W（测试条件 3.8 万 lux 强光） |
| 类型     | 多晶硅，环氧滴胶封装                  |
| 引线     | 14 cm 红黑线，红正黑负                |
| 工作温度 | −20 ℃ ~ 60 ℃                       |

### 3.2 为什么不能直接给 ESP32 供电【已定】

1. **电压不够**：开路 1.8V，低于锂电池 3.7V，必须升压；也低于 ESP32 工作电压。
2. **TP4056 用不了**：TP4056 属线性充电，要求输入约 4.5–5.5V，低压板根本进不去。
3. **功率太小**：峰值 0.12W。ESP32 开 WiFi 瞬时可达 80–250 mA，屏幕背光、GNSS 更是耗电大户，板子供不上会反复掉电重启。
4. **无保护会反充**：夜间或弱光下电池会倒灌太阳能板，损坏板子。

### 3.3 正确链路【已定】

```
太阳能板 → MPPT 低压升压充电模块（CN3065 / CN3791 类）→ 锂电 → 负载
```

选型要点：

| 参数         | 要求                                | 原因                            |
| ------------ | ----------------------------------- | ------------------------------- |
| 启动电压     | 越低越好（CN3065 类可低至 0.9V 级） | 弱光下也能起充                  |
| MPPT         | 必须具备                            | 小功率板不加 MPPT 效率极低      |
| 防反充       | 必须具备                            | 防止电池倒灌                    |
| 充电电流可调 | 具备                                | 匹配 0.12W 板，避免拉垮板子电压 |

### 3.4 ETC 太阳能板的可行性

ETC 车载单元上的太阳能板属于**弱光涓流型**，典型输出仅几 mA 到 20 mA 量级，设计目标是维持 ETC 内部小电池待机，不是持续供电。

结论：**可以接，但只能做涓流补电，不能作为主力电源**。若要用，同样必须经过 MPPT + 防反充模块，不能直连。

### 3.5 功耗预算与续航判断【已定判断，数值待实测】

核心矛盾：**充电功率远小于活跃功耗**，因此太阳能方案成立的唯一前提是把平均功耗压到极低。

降低平均功耗的手段（按收益排序）：

1. **屏幕是最大变量**：改用半反射屏，白天关背光，功耗可降一个数量级。
2. **深度休眠**：非骑行时段进入 deep sleep，仅保留 RTC 与充电回路。
3. **外设电源门控**：GNSS、风速、手臂 IMU 用 MOS 管独立切断，不靠软件 stand-by。
4. **降低采样与上报频率**：姿态 25–50 Hz 足够，不必 100 Hz 以上。
5. **关闭常驻 WiFi**：仅在停车同步记录时开启。

> 结论表述要求：对外描述时必须说明"太阳能只能延长续航、不能实现无限续航"，阴天、树荫、夜骑场景仍会净耗电。

## 4. 显示与人机交互

### 4.1 屏幕方案对比

| 方案                           | 户外可读性             | 夜间可用       | 功耗               | 结论                     |
| ------------------------------ | ---------------------- | -------------- | ------------------ | ------------------------ |
| 普通 IPS/TFT（现有）           | 强光下发白，基本不可读 | 可用           | 高                 | 不适合户外主场景         |
| **ST7789S 半反半透彩屏** | 强光下靠反射，清晰     | 开背光可用     | 中（白天可关背光） | **推荐，日夜两用** |
| RLCD 纯反射屏                  | 极佳，光越强越清晰     | 不可见，需补光 | 极低               | 仅适合白天骑行场景       |

### 4.2 选型建议【已定】

- 若需日夜两用：**ST7789S 半反半透**，白天关背光、夜间开背光。
- 若只白天骑行且追求极致低功耗：**RLCD**。
- 接口均为 SPI，驱动库与常规 ST7789 通用，切换成本主要在背光控制与配色（半反屏对比度低，UI 需改为高对比、少渐变）。

### 4.3 主板选择

优先选择**板载锂电充放电管理 + 板载六轴 IMU** 的 ESP32-S3 开发板（如微雪 ESP32-S3-Touch-LCD 系列），理由：

1. 省去自建充电电路，减少故障点。
2. 板载 IMU 可作车架基准 IMU，减少外接走线与磁干扰源。
3. 已有屏幕与外壳生态，迭代快。

> 【待验证】具体型号的充电输入电压范围、是否支持太阳能输入、IMU 型号与量程需查规格书确认。

## 5. 姿态识别体系（核心章节）

### 5.1 两个 IMU 的角色定义【已定】

| 传感器        | 安装位置                  | 角色               | 输出意义                               |
| ------------- | ------------------------- | ------------------ | -------------------------------------- |
| IMU-A（板载） | 码表本体，固定于车把/车架 | **车架基准** | 车身俯仰、横滚、航向；爬坡、压弯、颠簸 |
| IMU-B（外置） | 穿戴于手臂                | **被测肢体** | 上肢局部姿态                           |

**核心认知：我们要的不是"手臂相对地面"的角度，而是"手臂相对车身"的角度。**

原因：上坡时车身本身抬头，若用绝对角度会误判；只有相对车身的角度才真正对应"人趴在车上的程度"。

### 5.2 佩戴位置评估【已定结论：前臂优于上臂】

| 位置           | 能捕捉什么           | 优点                                                                       | 短板                                                     | 适配结论                     |
| -------------- | -------------------- | -------------------------------------------------------------------------- | -------------------------------------------------------- | ---------------------------- |
| 心率胸带 IMU   | 躯干俯仰、脊柱弯曲   | 位置稳定，兼顾心率                                                         | 完全看不到手臂；深呼吸、耸肩带来噪声                     | 仅辅助，不可做主判据         |
| 上臂           | 大臂前伸/下压        | 自由度少，不易自转；佩戴方便                                               | **与迎风面积相关性弱**；肱二头肌充血易导致绑带位移 | 次优                         |
| **前臂** | 小臂抬升角、内收外展 | **与迎风投影面积直接强相关**；计时把姿势下摆动小；不易受肌肉膨胀影响 | 手腕旋前/旋后引入自转噪声；摇车时甩动大                  | **首选**               |
| 头盔           | 头部俯仰             | 无束缚，安装方便                                                           | 自由度最高，看码表/抬头即失效；头盔本身晃动噪声大        | 优先级最低，原型阶段直接不做 |
| 上臂 + 前臂    | 可推算肘关节夹角     | 能区分"开肘假低趴"与"收肘真低趴"                                           | 两节点，同步与功耗成本上升                               | 二期升级路径                 |

**为什么前臂更有效（关键论证）**

低风阻姿势的本质是减小迎风投影面积，而投影面积主要由**小臂的空间指向与肘部开合**决定。上臂只决定肩的基座位置，同样的大臂角度下，小臂翘起或摊开会让风阻显著上升，而上臂 IMU 完全感知不到这个变化。因此对 CdA 量化目标而言，前臂是**直接观测量**，上臂是**间接观测量**。

### 5.3 单侧还是双侧【已定：单侧右臂】

- 公路车稳态巡航时双手对称握把，左右上肢姿态高度一致，单侧即可代表整体。
- 双侧方案硬件翻倍、BLE 连接数翻倍、丢包概率上升、佩戴负担加重，性价比显著下降。
- 只有研究**左右发力不对称、肩高不平衡**时才需要左侧，属于后续课题，不属于本版。

### 5.4 坐标系定义与安装约定

三套坐标系（右手系）：

| 记号 | 含义                                                               |
| ---- | ------------------------------------------------------------------ |
| G    | 全局坐标系（大地）。Z 轴指向重力反方向，X 轴指向正北（地磁可用时） |
| B    | 车架坐标系（IMU-A）。X 轴指向车头前进方向，Z 轴垂直车架向上        |
| L    | 肢体坐标系（IMU-B）。随手臂运动                                    |

**佩戴约定（用于简化算法、减少歧义，不是硬编码角度）**

> IMU-B 贴于**右前臂外侧**，基准姿势下使其 X 轴尽量顺着小臂指向手腕方向。

即便贴歪也不影响正确性，只需在标定阶段补偿。统一佩戴朝向的意义在于避免滚转符号翻转，让调参可控。

### 5.5 标定流程（每次骑行前执行）

**不要写死一个固定偏移角。** 任何硬编码的角度在换绑带位置、换人、换车后都会失效。

标定步骤：

1. 骑行者保持**标准基准姿势**（如计时把巡航姿势）静止 3 秒。
2. 同时读取 IMU-A 四元数 `q_A`（车架→大地）与 IMU-B 四元数 `q_B`（手臂→大地）。
3. 计算安装偏差四元数：

```
q_offset = q_A⁻¹ ⊗ q_B
```

4. 该 `q_offset` 即"IMU-B 相对于车架的固定安装偏差"，包含绑带贴歪角度与芯片焊盘安装偏角，缓存备用。

运行时（每帧）：

```
q_rel = q_A⁻¹ ⊗ q_B ⊗ q_offset⁻¹      # 手臂相对车架的真实姿态
```

从 `q_rel` 中提取：

- **相对俯仰 Pitch_rel**：小臂抬升/下压角（主判据）
- **相对偏航 Yaw_rel**：小臂向内收拢/向外摊开角（辅助判据）
- **相对滚转 Roll_rel**：小臂自转（**不参与打分，直接丢弃**）

> 只使用俯仰与偏航两个自由度；滚转对应手腕旋前旋后，与风阻无关且噪声大。

### 5.6 地磁能不能用来判断两点的相对位置【已定：不能测距】

必须澄清一个常见误解：

- 地磁是**方向信号**，不是**距离信号**。两个 IMU 的地磁数据相减只能得到**航向差**，永远得不出"手臂离车把多远"。
- 可用于：计算上臂/小臂相对于车身的**左右外展角（Yaw_rel）**，作为"开肩/收肩"的辅助特征。
- 不可用于：定位、测距、判断前后远近。

**地磁的三个现实问题**

1. **车架磁场畸变**：钢架、不锈钢辐条、刹车碟、花鼓、螺丝、供电线电流都会扭曲本地磁场。车把处的 IMU-A 受影响最大，而手臂端受影响小，两者畸变不同源，航向差的固定偏移会随拆装、换轮变化。
2. **必须做水平投影**：航向解算只在水平姿态下成立，车身俯仰/压弯时直接用磁力计航向必然失真，必须先用四元数把磁场矢量投到水平面。
3. **动态跟随差**：磁力计响应慢，摇车、转向时跟不上，无法提供瞬时动态角。

**碳纤维车架/碳辐条能改善多少**

| 干扰源                    | 换碳架后           | 说明                               |
| ------------------------- | ------------------ | ---------------------------------- |
| 钢架、钢辐条的静磁畸变    | **显著减弱** | 碳纤维无铁磁性，不扭磁场           |
| 铝/钛紧固件、不锈钢刹车碟 | 部分减弱           | 仍存在，多数碳轮方案仍保留金属碟片 |
| 电路电流产生的交变磁场    | **无改善**   | 与车架材质无关，是码表自身电路引入 |
| 倾斜带来的算法误差        | **无改善**   | 属于解算原理问题                   |

结论：碳架能让航向零点更稳定、标定一次用更久，属于**锦上添花**；为地磁算法专门换车架**性价比很低**，软件标定与滤波才是正解。

**本版对地磁的处理【已定】**

第一版原型只**记录** Yaw_rel 到日志，**不参与打分**。先把 Pitch_rel 主链路跑稳，路测看噪声水平，确认信噪比后再决定是否引入修正项。所有算法模块都保留 `mag_weight` 参数，可随时降级为纯六轴模式。

## 6. 通信方案：BLE 与 ESP-NOW

### 6.1 对比

| 项目       | BLE（成品模块）              | ESP-NOW（自建 ESP32 节点） |
| ---------- | ---------------------------- | -------------------------- |
| 延迟       | 20–80 ms，有明显抖动        | 1–10 ms，稳定             |
| 丢包       | 手臂摆动遮挡易丢包           | 丢包率低，有 ACK           |
| 连接数     | 主从配对，稳定连 2–3 个从机 | 无连接，可广播接收多节点   |
| 时间戳对齐 | 难，需插值补偿               | 易于统一时间轴             |
| 开发量     | 小，只需主机侧解析           | 大，需自研从机固件与低功耗 |
| 功耗       | 成品模块已做优化             | 需自行设计休眠策略         |
| 成本       | 直接用                       | 每节点需 ESP32-C3 + IMU    |

### 6.2 决策【已定】

- **一期**：使用已购成品 BLE 六轴模块（WT901 类），只做单节点，快速打通算法闭环。
- **二期**：自制 ESP32-C3 + IMU 节点，改用 ESP-NOW，解决同步与丢包；同时支持上臂 + 前臂双节点。

### 6.3 一期 BLE 的应对措施【已定】

1. **时间戳对齐**：利用 BLE 包内帧序号 + 接收时刻，建立映射；把手臂姿态**线性插值**到车架 IMU 的固定采样时间轴（50 Hz）上，消除到达抖动。
2. **丢包容错**：设 250 ms 超时门限；短时丢包（1–2 帧）沿用上一帧，超时则标记姿态无效，冻结打分，不参与 CdA 计算。
3. **优先读四元数**：读取模块内置 AHRS 的四元数输出，不要在主机侧只取欧拉角，避免万向锁与插值困难。
4. **架构预留**：解析层、融合层、打分层、呈现层分离；二期换 ESP-NOW 只替换解析层。

### 6.4 ESP-NOW 的硬约束

- ESP-NOW 与 WiFi 共用 2.4 GHz，**骑行全程禁止开 WiFi**，仅在停车同步时开启。
- ESP-NOW 本身不做姿态解算，AHRS 滤波需在节点端或主机端自行实现。
- 节点必须做 deep sleep + 定时唤醒采样，否则续航不可接受。

## 7. 算法要点

### 7.1 两层结构，不要混在一起改

| 层                           | 作用                                                         | 是否可变                |
| ---------------------------- | ------------------------------------------------------------ | ----------------------- |
| **L1 单 IMU 姿态估计** | 每个 IMU 各自输出相对大地的四元数                            | ✅ 这是算法对比的战场   |
| **L2 相对姿态求解**    | `q_rel = q_A⁻¹ ⊗ q_B ⊗ q_offset⁻¹`，再解出 Pitch/Yaw | ❌ 数学上唯一，固定不动 |

把所有可变性收在 L1，L2 只写一次，后续换算法不影响下游。

### 7.2 三级噪声过滤【已定】

1. **冲击过滤（颠簸/过坑）**：`|gyro|` 超过阈值时丢弃当前帧，保持上一有效姿态。
2. **丢包/超时过滤**：BLE 250 ms 超时则冻结姿态，不切换分区。
3. **低通平滑**：对 Pitch_rel 做一阶低通，时间常数 0.2–0.4 s。

### 7.3 姿态打分函数

输入：滤波后的 `Pitch_rel`（可选加权 `Yaw_rel`）

```
score = clamp(Pitch_rel, P_min, P_max) 线性映射到 0–100
```

两个关键标定点需实测确定：

- `P_min`：直立握把时的 Pitch_rel（对应 0 分）
- `P_max`：稳定 TT 深度破风姿势的 Pitch_rel（对应 100 分）

带 Yaw 修正时：

```
score = score_pitch × (1 − k × max(0, |Yaw_rel| − deadband) / Yaw_span)
```

`deadband` 建议 7–10°，避免残余噪声导致持续扣分。

### 7.4 七级气动分区映射

| 分区   | 分数区间 | 姿态描述     | CdA 修正系数（示例，需实测校准） |
| ------ | -------- | ------------ | -------------------------------- |
| Zone 1 | 0–14    | 完全直立     | 1.00（基准）                     |
| Zone 2 | 15–28   | 轻微前倾     | 0.94                             |
| Zone 3 | 29–42   | 小幅低趴     | 0.88                             |
| Zone 4 | 43–56   | 常规巡航低趴 | 0.82                             |
| Zone 5 | 57–70   | 较好气动姿势 | 0.76                             |
| Zone 6 | 71–84   | 优秀破风姿势 | 0.70                             |
| Zone 7 | 85–100  | 极限深度低趴 | 0.64                             |

> 【待验证】表中修正系数为示例值，必须通过实测（功率—速度—风速联合反算）标定，不可直接作为产品数据发布。

**分区切换防抖**：分数稳定落在新区间并持续 ≥ 1.0 s 才切换；瞬时越界不触发，避免 UI 与日志频繁跳变。

### 7.5 CdA 融合

```
CdA_real = CdA_base × K_pose(score)
```

- `CdA_base`：由车速、相对风速、功率、坡度反算的基础风阻面积。
- `K_pose`：由姿态分数查表得到的修正系数。
- 坡度、侧风、车轮旋转扰动作为**独立修正项**，不与姿态因子混为一谈。

### 7.6 当前方案的能力边界【局限】

1. **无法区分开肘/闭肘**：单前臂一个 IMU 时，大臂角度相同但肘部开合不同的两种姿势会得到相近分数，这是最大误差来源，二期加前臂/上臂双节点才能解决。
2. **默认左右对称**：摇车、单侧发力时可信度下降。
3. **BLE 同步精度有限**：依赖插值，精度弱于 ESP-NOW。
4. **地磁航向不可靠**：受车架与电路磁场影响，只能辅助。
5. **纯六轴偏航必然漂移**：这是物理不可观测性，不是算法优劣问题，必须靠周期性重标定缓解。

## 8. 算法模块化与离线对比框架

### 8.1 为什么必须模块化【已定】

在车上反复改固件试错的成本极高（每次上车、每次颠簸、每次天气不同）。正确做法是：**一次采集原始数据，在电脑上离线回放，多算法并行对比**，用 RMSE、漂移速率、单帧耗时等指标选赢家，而不是靠"感觉差不多"。

### 8.2 统一接口设计

```c
typedef struct {
    const char *name;
    void  (*init)  (ahrs_t *self, float fs);              // 采样率
    void  (*update)(ahrs_t *self, const imu_sample_t *s); // 灌一帧
    void  (*get_q) (ahrs_t *self, quat_t *out);           // 输出四元数
    float (*get_conf)(ahrs_t *self);                       // 可信度 0~1，供 L2 加权
} ahrs_ops_t;
```

要点：

1. **编译期只编进 1–2 个算法**：ESP32 内存有限，不要全量编译；用宏或注册表按需选择。
2. **L2 只认四元数**，不感知 L1 用了哪套算法。
3. **原始数据先落盘再算**：所有算法必须跑在同一份 `imu_sample_t` 序列、同一 fs、同一时间戳上。

### 8.3 候选算法清单（真实可实现、ESP32 可跑）

| 模块                   | 原理                  | 优点                       | 短板                       | 定位               |
| ---------------------- | --------------------- | -------------------------- | -------------------------- | ------------------ |
| `ahrs_gyro_int`      | 纯陀螺积分            | 最轻、动态最快             | 倾角会漂，几秒即失效       | 基线对照           |
| `ahrs_accel`         | 加速度算倾角          | 静态绝对准、零漂           | 一颠簸就失效               | 基线对照           |
| `ahrs_complementary` | 加速度低频 + 陀螺高频 | 轻量、参数直观             | 无磁时偏航漂移             | 基线               |
| `ahrs_madgwick`      | 四元数梯度下降        | 开源、算力低、精度好       | 纯六轴偏航长期漂移         | **主推候选** |
| `ahrs_mahony`        | 四元数 PI 互补        | 算力更省                   | 收敛稍慢                   | 主推候选           |
| `ahrs_ekf`           | 误差状态卡尔曼        | 精度最高，可输出协方差自评 | ESP32 上算力吃紧，参数难调 | 备选               |
| `ahrs_dmp`           | 成品 IMU 内置解算     | 零算力、最稳               | 不可调参                   | 现成模块方案       |

### 8.4 离线评测流程

```
一次骑行实测（固定 50 Hz）
   → 原始 acc/gyro 落盘（CSV 或二进制）
   → 电脑端 C 程序：同一份数据灌进各算法模块
   → 输出指标：RMSE、漂移速率(°/min)、抖动标准差、单帧耗时(μs)
   → 选定赢家写回 ESP32
```

**没有光学动捕时的低成本真值替代方案**：

1. **静态多位置实验**：把传感器置于已知角度的静止位置（0°/15°/30°/45° 等），各静止 30 秒，用转台或量角器提供参考真值。
2. **一致性检验**：动态段用多算法互证，差异大的时段回看原始数据，判断谁先漂。

### 8.5 实施顺序

| 阶段 | 产出                                                       |
| ---- | ---------------------------------------------------------- |
| 1    | `imu_sample_t` 结构 + 原始日志落盘 → 一份可复现的数据集 |
| 2    | 电脑端离线评测框架，先接 3 个基线算法验证接口              |

| 4    | 视结果决定是否引入 EKF                                     |
